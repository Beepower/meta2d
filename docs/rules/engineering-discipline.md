## 这份文档讲什么

这份文档是 meta2d.js 项目 AI 实施者的高频失败模式库，配套自查清单，供 AI 在每次汇报前对照使用。适用范围是 meta2d 项目 P1+ 阶段，所有规则永真生效，不需要每个阶段重新校准。

与 `docs/rules/engineering-vision.md` 的分工：本文件讲**怎么做**——R8 失败形态识别、Q 自查清单、对称约束反向应用、轮次度量、基线规则；engineering-vision.md 讲**做什么**——V1 行为如何分类、接口设计哲学。

与 `docs/rules/AI-cooperate.md` 的关系：

> AI-cooperate.md 是**正面规则**——AI 该做什么（六条 P1-P6 准则）。
> 本文件是**反面案例库**——AI 容易栽在哪里（meta2d 项目实际撞过的 R8 失败形态，以及对应的 Q 自查清单）。
>
> R8 形态本质上是 AI-cooperate.md 中 P4「行行有据」反模式（事后追认 / 判断甩锅）和 P5「临疑能止」反模式（硬撑）的具体表现。本文件提供 meta2d 项目里这些反模式的实际触发案例，帮助 AI 识别"这次任务正在接近哪种失败模式"。

## R8 形态与自查清单

R8（自反类反模式——自引入 / 自欺类）是 P0 期间识别的大模型实施者高频失败模式。每个形态对应一条自查问题，向用户汇报前必答。

### R8 形态矩阵

| 形态 | 现象 | 对应自查 | P0 触发案例 |
|---|---|---|---|
| **R8-1** | 把"我能做的部分"算"完整完成"（漏做） | **Q1** | 把 quirks 推到 S4 / S1.2 工时偏差假装达标 |
| **R8-2** | 自己引入新方案体系然后假装是既定的 | **Q2** | (A)(B)(C) 三层标签自引入 → D-P0-17 §4 撤回 |
| **R8-2'** | 把结构改动伪装成实施注记 | **Q5 v3** | jsdom → happy-dom 默认自决（D-P0-31）|
| **R8-3** | 把用户的非显式表态解释成显式裁决 | **Q5 v1** | P0 退出门槛 5 ✅ 误判（D-P0-19）|
| **R8-4** | *（保留——跳号反映真实识别历史，未来形态浮现时填入）* | — | — |
| **R8-5** | 用估算替代逐条枚举 | **Q6** | S5 v1 6 类按估算 → v2 重做逐条枚举（D-P0-28）|

**辅助自查**（不绑定单一形态）：
- **Q3** — 自查的机器化盲区（grep / 文件查询能覆盖 vs R8 苗头需要工程审美来识别）
- **Q4** — 价值发现漏（数据已经暴露但是没说出来）

> **R8-4 保留的工程含义**：编号承载历史。跳号本身就是提醒——"这里之前出过盲区，待后续阶段浮现时填入"。线性重新编号会丢失历史信号。

### Q1-Q6 自查清单

每次向用户汇报前必须显式回答 Q1-Q4。Q5 和 Q6 是特定动作触发，不是每次汇报都要答。

| # | 自查问题 | 触发时机 | 失败处置 |
|---|---|---|---|
| **Q1** | 我有没有把"我能做的部分"算"完整完成"？ | 每次汇报前 | R8-1 触发 → 重做整个 S |
| **Q2** | 我有没有引入新概念（列表 / 选项 / 分类 / 标签）然后假装是既定的？ | 每次汇报前 | R8-2 触发 → 重做整个 S（显式标"新提议"或者撤回）|
| **Q3** | 自查是机器化（grep / 文件查询）还是工程审美（识别 R8 苗头）？机器化够吗？ | 每次汇报前 | 机器化不够 → 补做 R8 苗头自查后重新汇报 |
| **Q4** | 我有没有价值发现没识别出来？（数据已经暴露但是没说出来）| 每次汇报前 | 补做价值发现段后重新汇报 |

| **Q5 v3** | 修订既存的唯一事实源（SSoT）决策内容时，原用户拍板时是否明确允许这一项自决？ | 修订既存 SSoT 内容时（`docs/decisions/D-P*-*` / `docs/rules/*` / `docs/master-plan.md` / `phases/P*/scope.md` / `cross-chasm.md` / 等）| 没明确允许 → 默认作为结构改动，向用户汇报 |
| **Q6** | 我汇总数据前是不是有逐条枚举？是不是跳过枚举直接给估算？ | 报告"~N 条某类"前 | R8-5 触发 → 等同 R8-1 漏做，重做整个 S |

**Q5 v1 触发示例**：

| 用户表态 | 想解释为 | 正确做法 |

| "P1 时再细分" | "已裁决"通过门槛 | 暂停发问"是 X 标签吗？（三选一 / 四选一中的哪一类）" |
| "看起来 OK" | "通过" | 暂停发问"通过哪个门槛？（具体审阅项）" |

### R8-2 与 R8-2' 的区别

| 形态 | 性质 | 例 |
|---|---|---|

## Q5 自查的三次扩展

Q5 专门处理"AI 把自己的判断当用户裁决"这类盲区，P0 期间扩展了三个版本。编号不连续（v1 → v3 跳号，同 R8-4 跳号），不重新编号。

| 版本 | 措辞 | 来源 S | 对应 R8 形态 |
|---|---|---|---|
| **Q5 v1** | "我有没有把用户的非显式表态（沉默 / 模糊 / 推迟方向）解释成显式裁决？" | S1.3.1 P0 退出门槛 5 ✅ 误判后引入 | R8-3 |
| **Q5 v2** | *（保留——P0 期间没独立写出；编号占位反映历史）* | — | — |
| **Q5 v3** | "任何动到既存 SSoT 决策内容的修订，默认作为结构改动向用户汇报，除非用户在原拍板时明确说'实施细节自决'" | D-P0-31 jsdom → happy-dom 之后 | R8-2' |

> **为什么不重新编 1/2/3？** 编号承载历史：跳号本身是提醒——"这里之前出过盲区，编号 v2 待后续阶段浮现时填入"。线性重编会丢失"原 Q5 v1 不能覆盖 v3 这种情况"的工程教训。

### Q5 v3 自问规则（修订决策档案时）

```
修订 D-P0 决策时，先问"原用户拍板时是否明确允许这一项自决"？
- 明确允许 → 标为实施注记合理
- 没明确允许 → 默认作为结构改动，向用户汇报
```

判定示例：

| 修订内容 | 性质判定 |
|---|---|
| vitest 版本号升级（1.6.1 → 1.7.0）| 标为实施注记合理（框架不变，争议小）|
| jsdom → happy-dom | **结构改动**（测试框架核心，行为不同）→ 必须向用户汇报 |
| 加 vitest-canvas-mock 进 setupFiles | **结构改动**（测试环境组件）→ 必须向用户汇报 |
| `coverage.provider: 'v8'` 改 `'istanbul'` | 中间地带（报告格式不同 → 偏向结构改动）→ 倾向汇报 |

### Q5 后续扩展模式

Q5 不是单次终点，是反复校准。后续阶段浮现新的大模型自欺盲区 → 加 v4 / v5 / ……，跳号保留遵循同样原则。

P0 期间已识别盲区累积：
- **Q5 v1**：大模型把用户模糊的表态当显式裁决（S1.3.1）
- **Q5 v2**：*保留*（P0 期间没独立写出；编号占位）
- **Q5 v3**：大模型把自己的实施判断当用户隐含同意（D-P0-31）

**后续校准流程**：识别新 R8 形态 → 给 Q 加新条目或扩展 → 起草 ADR → 追加到本节与 R8 形态矩阵。保留编号（比如 Q5 v2）由后续阶段浮现时填入，不重编现有版本号。

## 对称约束的反向应用累积

对称约束在 P0 期间累积了 4 次反向应用，每次扩展约束的适用边界。

**对称约束**（D-P0-19 §2，S1.3.2 d 用户拍板）：

> 用户审阅时的期望值与 Claude Code 的实际数据不一致时，优先信数据，用户调整期望（不要逼 Claude Code 改产物去匹配错误的期望）。

| 次 | 触发场景 | 信息状态 | 调整方向 |
|---|---|---|---|
| **1（D-P0-23）** | 用户拍板内部矛盾（选项 1 / 2 数据不相容）| 矛盾 | 用户调整拍板（Claude Code 不替用户选选项）|
| **2（D-P0-27）** | G-001 在 D-P0-18 推迟到下一阶段 | S3 数据让信息变充分 | P0 收口前裁决（不再推迟）|
| **3（D-P0-29）** | S5 v1 估算"B = 0"，推到 P1 覆盖 | v2 逐条枚举 C = 38，信息充分 | P0 收口前裁决 |
| **4（D-P0-32 §13 预备）** | 11h 18 条裁决从 D-P0-32 二分类视角重新审阅 | S7.6c 审阅之后 | 实际未触发（模式固化的兜底；S7.6c 18 条裁决全部一致）|

### 模式固化

> **逐条枚举完成 + 信息充分时，11h 类队列必须在 P0 收口前裁决，推迟是例外。**

每个阶段期间出现新数据让旧拍板的信息不足时，用户必须重新审视，不能默认推迟。Claude Code 责任：数据充分时主动浮出价值发现，让用户重新评估推迟决策。

### 正向与反向总结

- **正向**（D-P0-19 §2）：数据与期望不一致时——
  - **Claude Code 责任**：显式标注 ⚠️ 偏差与数据驱动的分析，向用户汇报（不沉默，也不悄悄改产物去匹配错误期望）
  - **用户责任**：先核对 Claude Code 的数据分析，数据正确就承认期望错了，调整期望

- **反向**（D-P0-23/27/29 累积）：用户拍板内部矛盾 / 信息变充分时——
  - **Claude Code 责任**：**主动浮出证据与价值发现，触发用户重新审视**。边界："不替用户解释"；义务："主动浮出触发"，二者不矛盾。具体：
    - 识别拍板内部矛盾 → 跑两套数据 + 显式列出矛盾 + 暂停发问让用户重新审视（S2.3 D-P0-23 案例）
    - 阶段期间出现新数据让旧拍板信息不足 → 主动浮出价值发现，让用户重新评估推迟决策（D-P0-27/29 模式）
  - **用户责任**：基于 Claude Code 提供的证据重新拍板（修矛盾 / 改推迟方向 / 等）

两个方向都是同一原则：**信息变化时双方主动重新审视，不要让错误状态延续**。Claude Code 的"主动浮出证据"和用户的"信息充分时重新审视"互为前提。

## 轮次度量

**估时用用户审阅轮次数，不用工作日**（D-P0-17，工作纪律 #4）。大模型与人的估时有 5-30 倍差距，工作日基线永远不可信。

### 轮次定义

- **1 轮 = 1 次汇报 + 用户审阅**
- 单个 S 内部 Claude Code 工时（脚本 6 秒 / 写文档 40 分钟）少于 1 小时不是关注点
- 关注点：**汇报的密度和质量**（完整性 / 是否有 R8 苗头 / 是否把校对推给用户）

轮次估时格式：`S_X ≈ 1 次汇报 + N 个用户审阅轮次`（N 由 S 复杂度与用户拦下来要求补强的次数估）。

### R8 苗头的三种失败处置

（D-P0-19 §3 (a)(b)(c)）

| 处置 | 触发 | 后果 |
|---|---|---|
| **(a)** | 用户审阅时发现 R8 苗头（Claude Code 没自查到）| **重做整个 S** |
| **(b)** | Claude Code 汇报前自查发现 + 显式记录 + 修正 + 汇报里说明 | **不触发失败，记为自查成功案例**（激励自查）|
| **(c)** | Claude Code 汇报前发现但没显式记录（悄悄改）| **等同于 (a)，触发失败，重做整个 S**（自查不透明 = 无效）|

### 为什么不简化为二分

如果严格"R8 苗头 → 重做"不区分自查 vs 被发现 → Claude Code 越积极自查越容易"触发然后被惩罚"，反向激励**不自查**。整套自查体系反向失效。

(c) 核心：**激励自查 + 透明记录，不是惩罚错误**。是自查规则本身的设计避免反向激励，不只是某一次 S 的修补。

### 其他失败处置（非 R8）

| 失败类型 | 处置 |
|---|---|
| 凭直觉（没用 grep / 没读文件验证）| 补做漏的部分，**不重做整个 S** |
| 漏价值发现（数据已经暴露）| 补做价值发现段 |
| 自查没真做（只跑了机器核对，或者把判断推给用户）| 补做 R8 苗头自查 |
| 没做双模式核对（D-P0-21）| 补做双模式核对 |

## 基线规则

以下基线规则 P0 期间累积，跨 S 永真：

### 校对纪律

**20% 校对必须真做** — 每个子里程碑工时分配的"50% 代码 + 30% 调试 + 20% 校对 + 回报"中，**20% 校对必须真做不能跳**。一个 S 完成的标准是全部可以机器核对的项目都核对完了。**不允许把校对推给用户**（S0b 正确性核对教训）。

### 可机器核对与待用户决策的区分

| 类型 | 处置 |
|---|---|
| 格式核对 / 文件存在性 / 字段落地 | **可机器核对** → 完成时必须自查 |
| 测试运行结果 / 数据正确性判定 / 设计决策 | **待用户决策** → 显式说"等用户跑测试"或"等用户决策" |

### 数据驱动优于直觉

（D-P0-19 §2 正向对称约束的运营落地）：

- 凭直觉判定 = 自查没真做 = 触发补做（不重做整个 S）
- 任何"看起来" / "应该是" / "通常"等措辞触发 Q3 自查——是不是有 grep / 读文件的证据？

### 双模式核对

（D-P0-21）任何基于 grep 限定接收方的判定（canvas / core / render / 卫星包 / 等）必须双模式核对：

```
1. 跑严格匹配模式（限定接收方列表）→ 命中 M
2. 跑宽匹配模式（任何接收方）→ 命中 N
3. 判定:
   - N > M * 1.3（差距超过 30%）→ 抽样审阅漏掉的（N - M 条），识别新接收方加进列表，重跑严格模式
   - N ≤ M * 1.3 → 严格模式是合理近似，接受
```

没做双模式核对 = 自查没真做 = 补做。

### 路径漂移核对

（D-P0-31 §5）每个新 S 开始时显式核对路径（`pwd` / `ls` 跑一次），避免绝对路径误用 / 工作目录漂移导致文件被写到错误位置。这是实施层面的基线规则，不加 D-P0 决策但纳入工作流程。

### cross-chasm.md §3.7 的四条协议起草纪律（引用）

1. **第 0 步永远先核对状态再做改动** — 不可逆操作的协议默认包含只读核对的第 0 步
2. **显式列出隐藏行为** — `.gitignore` 的宽匹配模式 / `.gitattributes` 过滤器 / submodule / git hooks / 跨平台 shell 差异
3. **显式承认用户进行中的工作** — 用 `git status` / `git log --since` 作为第 0 步强制核对
4. **跨平台命令显式表达** — 避免 Unix 特有的管道写法；或者显式标注 "Linux/Mac" + "Windows PowerShell" 两种等价写法

### meta2d 实践案例：Day 0b 文档迁移协议

Day 0b 文档迁移协议（`docs/refactor-public-api/day-0b-migration-protocol.md`）执行时三次浮现意外，每次都印证 cross-chasm.md §3.7 第 1-4 条：

| 次 | 浮现的意外 | 对应 cross-chasm.md §3.7 哪一条 | 起草时如何避免 |
|---|---|---|---|
| **1** | V2 仓的实际 inventory 是 37 个文件，不是起草时假设的 17（99-progress 已改名 / 多了 SESSION-KICKOFF / 多了 11-scan-scripts 整目录 / _archived 多 1 个）| 第 3 条用户进行中的工作 | 起草前用 `git ls-files` 查询，不要默认假设状态是静态的 |
| **2** | meta2d 仓根目录 `.gitignore` 里 `*.yaml` 这条宽匹配模式把 `pnpm-lock.yaml` 默默拦下了（V2 仓里这是被 git 跟踪的唯一一个 yaml 文件，被静默丢失）| 第 2 条隐藏行为 | 起草前查一下 `.gitignore`，跑一下 `git check-ignore` 核对暂存范围 |
| **3** | V2 仓有暂存但未提交的重命名（`99-progress.md → _archived/`），是 P0 收口期用户进行中的工作 | 第 3 条用户进行中的工作 | 用 `git status` 显式列出暂存 + 工作树状态，不要默认是干净的 |

**元教训**：三次都不是用户或者 Claude Code 的失误，**而是 skill 起草的协议自身不完整**。起草前应用这 4 条可以避免这件事。
