## 概述

本文件是 meta2d.js 重构项目的工程视野基线——回答的问题是"V1 上帝类（god-class）11 月演化的现象，在 P3/P4 切换时如何区分接口契约（surface 契约）vs 设计松散债"。

P0 期间通过 quirk 11.2 #6 浮现总原则（D-P0-32 扩展 v2），S7.6 实测 95 条 A' 行为之后细化到三维度分类（D-P0-34）。本文件提炼 P0 期间累积的工程视野原则，作为 P1+ 跨阶段永真规则。

与 `engineering-discipline.md` 的关系：

- `engineering-discipline.md` = **怎么做**（工程的 R8 / Q / 对称约束 / 轮次 / 基线规则）
- `engineering-vision.md` = **做什么**（V1 行为如何分类 / 工程债如何摊销 / 接口设计哲学）

## V1 行为二分类原则

### 1 核心表达

> **V1 行为默认砍掉（归设计松散债）+ 只有 V2 / 卫星调用点实际依赖的保留（归接口契约）。**

**两大类**：

| 类 | 含义 | P3/P4 处置 |
|---|---|---|
| **设计松散债** | V1 上帝类 11 月演化的设计松散现象 | P3/P4 不默认保留；P3 审视 V2 调用点调整改接口抽象 |
| **接口契约** | V2 / 卫星调用点实际依赖的 V1 行为 | P3/P4 切换时必须由接口覆盖 |

**判定证据**：

- `11d-satellite-call-sites.md`（卫星 12 个调用点 / 6 个文件，真实 grep）
- `11e-v2-call-sites.md`（V2 195 个调用点 / 15 个文件，真实 grep）
- 业务逻辑判断（部分需要用户拍板）

### 2 触发案例：quirk 11.2 #6（D-P0-32 第 6 节）

S6 撞 quirk 11.2 #6（`canvas.addPen` 默认 emit=undefined，`Meta2d.addPen` 默认 emit=true，门面（facade）默认值不一致），用户挑战工程视野时浮现总原则：

| 路径 | emit 默认值 | 二分类归属 | P3 处置 |
|---|---|---|---|
| `canvas.addPen(pen)` | emit=undefined 不发 'add' | **设计松散债** | P3 砍掉 emit 参数（V1 上帝类方法签名不一致）|
| `Meta2d.addPen(pen)` | emit=true 发 'add'（门面默认值）| **接口契约** | P3 保留门面默认语义（V2 业务层监听器真实依赖此路径）|

具体案例浮现的不只是单条 quirk，是**整个 V1 上帝类的设计哲学问题**：V1 行为不能默认都视为接口契约。

### 3 累积逻辑（D-P0-32 第 7 节）

二分类原则是 P0 期间多个 D-P0 现象的统一表达：

| D-P0 | 现象 | 二分类视角 |
|---|---|---|
| **D-P0-22** Meta2d 门面混合委托（mixed-delegate）| 门面改默认参数语义 / 加参数 / 包一层逻辑 | 混合部分如果 V2 依赖 → 契约；V2 不依赖 → 工程债 |
| **D-P0-24** 同名重叠 11+ 个方法 | canvas 与 Meta2d 方法签名不一致 | 方法签名分化属于工程债；门面默认语义如果 V2 依赖属于契约 |
| **D-P0-25** 遗忘公共方法（forgotten-public）224 个死代码 | 门面类 export + V2 / 卫星 grep 命中 0 | 全部属于工程债（V2 / 卫星命中 0 即定义不在契约）|

三个 D-P0 都是 V1 上帝类的设计松散现象，**P3/P4 不默认保留**。D-P0-32 扩展 v2 是这三个现象的统一表达。

### 4 工程基础（D-P0-32 第 8 节）

V1 行为 ≠ 接口 v1.0 必须保留的契约：

- 接口 v1.0 是 V2 团队 8 天设计冲刺的产物（15 个访问器 / 119 个 API / 47 个事件 / 4 大设计选择）
- 设计意图是**主动消除 V1 上帝类 11 月演化的设计松散**，不是把 V1 行为照搬到 v1.1
- P0 → P1 桥的产出**不应该**当作 "V1 行为清单" 给 P1——应当作 "V1 设计松散债 vs 接口契约二分类清单"

## 三维度子分类

### 1 三维度定义（D-P0-34 第 1 节）

简单二分（契约 vs 工程债）不足以表达 V1 上帝类的真实形态。S7.6b 实测 14 条混合形态（方法签名属于工程债 + V2 实际依赖部分行为 / 事件属于契约），引入第三维度：

| 维度 | 含义 | 数量（S7.6b 实测，本规则修订后）|
|---|---|---|
| **契约** | V2 / 卫星真实依赖 V1 行为，P3 完整保留 | 47 |
| **债** | V1 上帝类设计松散，V2 不依赖，P3 完整砍 | 34 |
| **混合** | 方法签名属于工程债 + V2 实际依赖部分行为 / 事件属于契约；P3 维度切分处置 | **14** |

**总 95 = 47 + 34 + 14 ✓**

11g 第 12 节二分类表格在原"分类"列基础上，显式标记维度数：

- **维度 1** = 纯契约 / 纯债（签名 + 行为 / 事件一致归属一侧）
- **维度 2** = 混合（签名一侧 + 行为 / 事件另一侧）

实施方式：11g 第 12 节不重写表格，在第 12 节末尾加维度数汇总表 + 交叉引用到第 3 节 P3 处置规则。

### 3 P3 处置三种（基于维度）（D-P0-34 第 3 节）

| 维度 | P3 处置 | V2 调用点 |
|---|---|---|
| **契约** | **完整保留** — 接口 v1.1 覆盖 V1 真实行为 | V2 透明切换（调用点不动）|
| **债** | **完整砍掉** — 接口 v1.1 主动消除 V1 设计松散 | V2 调用点审视调整（走接口抽象）|
| **混合** | **维度切分处置** — 方法签名砍 + V2 真实依赖的行为 / 事件保留 | V2 部分调用点审视 + 部分透明 |

**核心**：P3 实施者拿 11g 第 12 节看 A' 95 不是简单二分 47/48，是三维度 47/34/14——14 混合需要切分处置策略。

### 4 14 混合具体形态逐条枚举（校对修订 vs P0 存档）

> ⚠️ **本节是 Day 1 起草期间 Q4' 自查浮现的校对修订版**。原 P0 存档 `99-progress-P0-full.md` L1400 D-P0-34 第 4 节表达把 onResize 列入 canvas A'，Day 1 起草本规则时识别 onResize 实际属于 D 类（纯渲染 / 内部方法，不进接口），不是 A' 混合。校对调整为 canvas A' = 10。详见"追溯与维护"节。

| 来源 | 数 | 具体方法 / 事件 |
|---|---|---|
| canvas A' | **10** | 5 个 beforeXxx 钩子（`beforeAddPen` / `beforeAddPens` / `beforeAddAnchor` / `beforeRemovePens` / `beforeRemoveAnchor`）+ `translatePens` + `delForce` + `updateValue` + 2 个 onMouse* 方法（`onMouseDown` / `onMouseUp`）|
| core A' | 1 | `pushChildren` |
| quirks A' | 1 | 11.2 #6（emit 默认值 canvas 端属于工程债 / Meta2d 端属于契约）|
| emits A' | 2 | `enter` / `leave`（业务的悬停用 = 契约；部分卫星包不用 = 工程债）|
| **总** | **14** | |

**注脚**：

- `onResize` 是 resize 事件处理器，canvas god-class 的 resize 处理入口，纯内部，**不入 14 混合**（属 D 类，P3 / P4 拆解时随渲染层迁移）。**P0 archive D-P0-34 第 4 节误归 A' 混合**（措辞 "3 onMouse*" 含 onResize），Day 1 校对识别 onResize 实际是 D 类。

- 5 个 beforeXxx 钩子（`beforeAddPen` / `beforeAddPens` / `beforeAddAnchor` / `beforeRemovePens` / `beforeRemoveAnchor`）属于混合形态。从两个角度看：
  - 方法签名层面：这 5 个钩子直接挂在 canvas 上对外暴露，让外部代码挂回调来拦截 canvas 的内部生命周期。这种设计是 V1 把内部状态直接暴露出去，按门面模式（facade）应该让 Meta2d 这层来转发钩子。所以方法签名属于工程债。
  - 实际行为层面：V2 业务层（流程图业务的"添加节点前先校验"逻辑）确实依赖这些钩子的触发时机。砍掉钩子机制 V2 业务会断。所以触发行为属于契约。
  - P3 切换：钩子注册入口从 `canvas.beforeAddPen(cb)` 迁到 `meta2d.beforeAddPen(cb)`（签名层修），但钩子触发时机和参数语义保持（行为契约）。

- 2 个 onMouse* 方法（`onMouseDown` / `onMouseUp`）也属于混合形态。从两个角度看：
  - 方法签名层面：这两个方法直接挂在 canvas 上对外暴露，是 V1 设计松散——按门面模式应该让 V2 这层 Meta2d 接收鼠标事件再分发，而不是 canvas 自己接。这部分属于工程债。
  - 实际行为层面：V2 业务层（卫星包）在自己的鼠标处理逻辑里包了一层 canvas 的鼠标事件分发机制，依赖了 canvas 内部把鼠标事件传给笔（pen）的具体路径。这部分属于契约。
  - P3 切换：方法签名要砍（V2 改走 Meta2d 门面），但鼠标事件分发的内部行为在新结构里保留（V2 卫星真依赖）。

## 工程债摊销

> **本节内容是 Day 1 提炼——没有独立 D-P0**。来源是 D-P0-32 扩展 v2 第 11 节（"工作量在 P1 和 P3 之间重新分配"）+ D-P0-34 第 5 节（P1 spike 工作量评估）+ S7.6 实测 95 条维度数。提炼上升一层，作为工程视野原则，不是某条 D-P0 的简单重述。详见"追溯与维护"节。

### 1 核心原则：工程债处理位置正确比工作量分布更重要

P3/P4 V2 切换时，每条 V1 行为 A' 落地到**哪个阶段处理**比"总工作量多少"更关键：

| 阶段 | 改动方向 |
|---|---|
| **P1 spike** | 覆盖数减少（47 + 14 混合契约侧 = ~61，原本简单二分假设 95）——P1 工作量略减 |
| **P3 V2 切换** | 审视 + 调用点调整工作量增加（34 纯债 + 14 混合债侧 = ~48 条）——P3 工作量增加 |
| **总** | 持平或略增 |

但是**工程债处理位置正确**带来的复利收益远超总工作量略增的成本：

- P3 一次性付清 V1 设计松散债（V2 调用点审视 + 走接口抽象）
- v1.1 接口干净（没有 V1 上帝类 11 月演化的累积松散污染）
- 后续 P4-P8 受益（适配器（adapter）拆解 / 卫星重写 / 性能优化 / 等都基于干净接口）

### 2 反模式：把工程债推到接口 v1.x 永久承载

**反模式现象**：把 V1 行为默认都视为接口契约 → 接口 v1.1 = "V1 行为照搬" → 设计松散债被永久固化在接口里 → P4-P8 每个阶段都要绕过 / 修补这些松散债 → 永久利息。

**触发条件**（识别警告）：

| 警告 | 含义 |
|---|---|
| "V1 行为 X 现在能跑，所以接口 v1.1 也得保留" | 把 V1 行为当真相基准——**错**（应该反过来：接口 v1.1 是 V2 团队的设计意图，V1 行为是被消除的对象）|
| "V2 不用 X，但是 X 是 canvas / Meta2d 的公共方法，删了就是破坏性变更" | 把"V1 已导出表面"当契约——**错**（D-P0-25 遗忘公共方法 224 全是工程债，V2 / 卫星 grep 命中 0 即定义不在契约）|
| "X 行为有 quirk，但 quirk 也是行为，得保留" | 把 quirk 的隐含行为当契约——**错**（quirk 11.2 #6 emit 默认值不一致属于工程债，P3 砍 emit 参数即可）|

### 3 摊销决策树

判断 V1 行为 X 应该 **P1 覆盖**还是 **P3 审视**：

```
1. 11d / 11e grep V2 / 卫星调用点命中 > 0?
   - 否 → 纯债（P3 砍，P1 不覆盖）
   - 是 → 2

2. 方法签名 + 行为 / 事件全部一致归 V2 依赖侧?
   - 全一致 → 纯契约（P1 覆盖接口 v1.1）
   - 部分一致（方法签名属于债 + 部分行为 / 事件属于契约）→ 3

3. 混合形态：维度切分
   - 方法签名砍（P3 审视 V2 调用点）
   - V2 真实依赖的行为 / 事件保留（P1 覆盖接口 v1.1）
```

### 4 跨阶段工作量 vs 价值的权衡

P0 → P1 桥的产出指导原则：

> **P3 多付一点审视成本（工程债一次性付清），换 P4-P8 永久接口干净。**

如果 P0 期间识别出某条混合形态信息不充分 → 默认推到 P3 审视（不是推到 P1 覆盖），因为 P1 覆盖一旦落地接口 v1.1 就难逆转，而 P3 审视是阶段内部工作。
